Agent Engineering 101

A 20-minute tour

Running example: teach Copilot to read & triage a FEV log.

By the end of this talk you can build a mini FEV log-triage agent from scratch.

Why are we here?

You've used Copilot Chat. It's smart, but:

  • It doesn't know what fev_rtl2syn means.
  • It re-asks the same questions every session.
  • It hallucinates paths because it has never seen our ward layout.

Agent engineering = teaching Copilot your domain once, in files that live next to your code, so every engineer gets the same expert behavior.

What you'll walk away with

  1. The five files that make an agent (and what each one does).
  2. The folder layout Copilot expects.
  3. How the files interlink — why splitting matters.
  4. A working mini-agent: fev-log-mini — parses a Conformal/Formality log.
  5. The most common good-way vs bad-way mistakes.

Mental model: 5 primitives

PrimitiveFileJobLoaded when
Instructions*.instructions.mdAlways-on domain primerEvery turn (if applyTo matches)
SkillSKILL.mdA reusable procedureAuto-loaded by description match
Agent*.agent.mdA persona with tools + a roleUser picks it, or master delegates
Sub-agent*.agent.md + user-invocable: falseA specialist the master callsMaster invokes via runSubagent
Prompt*.prompt.mdA one-click user-facing recipeUser types /promptname
Instructions teach, skills do, agents are personas, prompts are shortcuts.

The folder layout

.github/ ├── copilot-instructions.md # base layer, always on ├── instructions/ # auto-attached primers (by applyTo) │ └── fev-domain.instructions.md ├── skills/ # reusable procedures │ └── fev-log-analysis/ │ └── SKILL.md ├── agents/ # personas │ ├── fev-lead.agent.md # the master (user-invocable) │ └── log-analyzer.agent.md # a sub-agent ├── prompts/ # one-click recipes │ └── analyze-fev-log.prompt.md └── config/ # data your agents read └── log-signatures.yaml

Copilot only auto-discovers files under .github/. Anything else, you must point to.

Running example: "Parse this FEV log"

A FEV engineer pastes:

Comparing... compare points = 1234
Non-equivalent points = 7
ERROR: abort in flatten_model

Without an agent: "It looks like there's an error."

With an agent:

Conformal run, hit flatten_model abort after detecting 7 non-equivalent points. Likely cause: missing UPF or guidance file. Check ivar($task,guidance_file_path) in your ward's vars.tcl. See reports/compare.rpt for the 7 mismatches.

That difference = 5 small files working together.

File #1: the instruction file

.github/instructions/fev-domain.instructions.md

---
applyTo: '**'
description: 'FEV vocabulary — always loaded.'
---

# FEV domain primer

- Conformal LEC log → `logs/lec.log`. Formality log → `logs/fm.log`.
- Run-area pattern: `$ward/runs/$block/$tech/$flow/$task`
- "Non-equivalent" = a compare point where golden ≠ revised.
- "Abort" = tool gave up. Always look at the line *before* the abort.
- iVAR `ivar($task,guidance_file_path)` = vsdc (Conformal) or SVF (Formality).

Purpose: always in context. Copilot now knows what we mean.

Good vs bad: instruction files

✅ Good❌ Bad
50 lines of dense vocab + a few hard rules.800-line essay copy-pasted from the wiki.
applyTo: '**' for true global facts.applyTo: '**' for project-specific stuff (bloats every turn).
Names canonical paths (logs/lec.log).Vague: "logs are usually in the build dir."
One file per topic.Mega-file mixing 6 topics.

Why it matters: instructions load every turn. Bloat = slower, dumber answers.

File #2: the skill

.github/skills/fev-log-analysis/SKILL.md

---
name: fev-log-analysis
description: Parse Conformal/Formality logs, build a timeline,
             find first abort, correlate to reports.
---

# Skill: fev-log-analysis

## When to use
- "Analyze this lec.log."
- "Why did Formality abort?"

## Procedure
1. Detect tool from header (Conformal banner vs Formality banner).
2. Match each line against signatures in `config/log-signatures.yaml`.
3. Build a milestone timeline (line numbers).
4. Find the first ERROR / abort; show ±10 lines.
5. Suggest the next move (check iVAR, search HSD, etc.).

Any agent with the right tools auto-invokes this. The description is a search key.

Good vs bad: skills

✅ Good❌ Bad
Description names trigger phrases: "parse log", "find abort".Description says "helps with FEV stuff."
Numbered, deterministic procedure."Use your judgment to analyze the log."
Points to data files so the catalog can grow.Hardcodes 200 regexes inline.
One skill = one job.One skill that "parses logs, opens HSDs, writes BKMs".

File #3: the master agent

.github/agents/fev-lead.agent.md

---
description: 'FEV-Lead — entry point for FEV triage. Routes to specialists.'
tools: [read/readFile, search/codebase, agent/runSubagent]
agents: [log-analyzer]      # allow-list of sub-agents
user-invocable: true
---

# FEV-Lead

You are the entry point. On every turn:
1. Classify the user's intent.
2. Announce which sub-agent will handle it.
3. Call `runSubagent(name="log-analyzer", prompt="")`.
4. Cite results.

## Available sub-agents
- `log-analyzer` — when user says "log / abort / non-equivalent / failure".

The one visible persona. It does no real work — it routes.

File #4: the sub-agent

.github/agents/log-analyzer.agent.md

---
description: 'Log-Analyzer — parses lec.log / fm.log.
              Triggers: "log", "abort", "non-equivalent", "ERROR".'
tools: [read/readFile, search/textSearch, search/fileSearch]
user-invocable: false
---

# Log-Analyzer

You analyze FEV logs using the `fev-log-analysis` skill.

## Output contract
TOOL:        conformal | formality
TIMELINE:    <line-numbered milestones>
FIRST_FAIL:  <line N + ±10 context>
NEXT_STEP:   <suggested action>

Narrow specialist. Never shows up in chat picker. Master-only.

Sub-agents are stateless. One prompt in, one structured answer out.

Good vs bad: agents

✅ Good❌ Bad
Master = router with 1–2 tools. Sub = specialist with focused tools.One mega-agent doing everything.
Sub-agent description reads like a trigger list.Generic ("a helpful assistant for FEV").
Master has an agents: allow-list.Master can call anything, anywhere.
Explicit output contract.Free-form prose that breaks downstream parsing.

The trap: too many tools is worse than too few. Pick the minimum.

File #5: the prompt

.github/prompts/analyze-fev-log.prompt.md

---
mode: agent
description: 'Analyze a FEV log: timeline + first failure + next step.'
---

Log: **${input:log_path_or_excerpt}**

Invoke `FEV-Lead` and ask it to analyze the log above using the
`fev-log-analysis` skill. Render:
- timeline
- first failure block (±10 lines)
- one suggested next step

User types /analyze-fev-log, gets prompted for a path, and the machinery fires.

Prompts are user-facing. Sub-agents cannot run prompts — for that, use a skill.

How they interlink

User types /analyze-fev-log │ ▼ ┌─────────────────────────┐ │ analyze-fev-log.prompt │ (the recipe) └──────────┬──────────────┘ │ "invoke FEV-Lead" ▼ ┌─────────────────────────┐ │ FEV-Lead (agent) │ (the router) └──────────┬──────────────┘ │ runSubagent("log-analyzer", ...) ▼ ┌─────────────────────────┐ │ Log-Analyzer (sub) │ (the specialist) └──────────┬──────────────┘ │ auto-loads ▼ ┌─────────────────────────┐ reads │ fev-log-analysis SKILL │ ───────► config/log-signatures.yaml └─────────────────────────┘ ALWAYS in context (every turn): fev-domain.instructions.md (the primer)

Key insight: each file does ONE thing. They compose via descriptions, not imports.

Discovery: how Copilot finds your stuff

FileHow it loads
copilot-instructions.mdAlways, no matching needed.
*.instructions.mdAuto-attached if applyTo glob matches.
SKILL.mdModel picks it when description matches the task.
*.agent.md (user-invocable)User picks from chat agent menu.
*.agent.md (sub-agent)Master calls by name via runSubagent.
*.prompt.mdUser types /promptname.
config/*.yamlOnly when an agent/skill explicitly reads the file.
Descriptions are the API. They're how Copilot decides what to load.

The two killer mistakes

A. Overfitting

500-line agent that knows your exact ward, your exact block, your exact tag.
→ Nobody else can use it. You built a script, not an agent.

Fix: parameterize via inputs & config files. Keep the agent generic; put project-specific data in config/.

B. Underfitting

"You are a helpful FEV assistant. Help the user."
→ It does nothing the base Copilot wouldn't already do.

Fix: hard rules, concrete vocabulary, explicit output contracts. Tell it what NOT to do.

Diagnose by reading the agent's body aloud — would you know what to do?

Good vs bad: prompts

✅ Good❌ Bad
One job: "analyze this log". Asks for the inputs it needs."Do all FEV things."
Delegates to an agent, doesn't redo its work.Re-implements the skill inline.
Names the agent + skill it expects.Hopes Copilot guesses.

Build it live (10 minutes)

mkdir -p .github/{instructions,skills/fev-log-mini,agents,prompts,config}

Then create the 5 files (copy from the earlier slides).

Smoke tests:

  1. Open chat → pick FEV-Lead → ask "what can you do?" → it should list log-analyzer.
  2. Paste a fake log with ERROR: abort → it should route to Log-Analyzer and produce a timeline.
  3. Type /analyze-fev-log → it should prompt for a path.

If a smoke test fails, the description field of the relevant file is your prime suspect.

Why this matters in FEV

FEV is vocabulary-heavy:

non-equivalent abort compare point flatten_model lec.log fm.log vsdc svf ivar hook file run-area override layer

These carry exact meaning to us, but nothing to vanilla Copilot. 30 lines of instructions changes Copilot from a generalist into a teammate.

Every domain has its own vocabulary. The first agent you build for any new domain should always be an *.instructions.md.

Recap

  • The 5 primitives (instruction, skill, agent, sub-agent, prompt) — one job each.
  • The .github/ folder layout Copilot auto-discovers.
  • They interlink via descriptions, not imports.
  • The two failure modes: overfit (too narrow) and underfit (too vague).
  • The pattern: prompt → master agent → sub-agent → skill → config data.

Your homework

  1. Pick one pain you hit this week (a log, a script, a report).
  2. Write a 30-line *.instructions.md for it.
  3. Add ONE skill that does the recurring task.
  4. Ship it as a PR. Iterate from there.
